# Ревью `app/Http/Controllers/BookingController.php`

Ревью проведено по коду контроллера, маршрутам (`routes/api.php`), моделям, миграциям и конфигурации
(`config/app.php` — таймзона приложения `UTC`, `config/logging.php` — канал `bookings`).

Обозначения серьёзности:

- **critical** — ломает основную функцию, приводит к потере/подмене данных или к уязвимости;
- **major** — нарушает бизнес-правило из ТЗ или даёт заметно неверный результат;
- **minor** — качество, консистентность, производительность без потери корректности.

## Critical

### C1. SQL-инъекция в `store`

```php
$conflict = DB::select("SELECT id FROM bookings
    WHERE room_id = {$request->room_id}
    AND starts_at <= '{$request->ends_at}'
    AND ends_at >= '{$request->starts_at}'");
```

Все три значения подставляются в SQL строкой. `starts_at = "2026-11-02T10:00:00+03:00' OR 1=1 --"` уже
ломает запрос, а через `room_id` можно подставить подзапрос и вытащить данные (например, токены из
`personal_access_tokens`, если у пользователя БД есть права на чтение).

**Как исправить:** использовать конструктор запросов с привязками (или Eloquent):

```php
$conflict = Booking::query()
    ->where('room_id', $room->id)
    ->where('starts_at', '<', $end)
    ->where('ends_at', '>', $start)
    ->exists();
```

Если принципиально нужен сырой SQL — только с bindings: `DB::select('... WHERE room_id = ?', [$roomId])`.
Заодно проверять, что `room_id` — существующая комната (сейчас несуществующий `room_id` даёт нарушение FK, то есть 500).

### C2. Автор брони берётся из тела запроса

```php
$booking = Booking::create($request->all());
```

В `App\Models\Booking` объявлено `#[Fillable(['room_id', 'user_id', 'starts_at', 'ends_at', 'title'])]`,
поэтому `user_id` из payload спокойно записывается в БД. Любой клиент может создать бронь от чужого имени
(README-пример это прямо провоцирует: `{"room_id": 1, "user_id": 1, ...}`), а `index` при этом покажет
бронь настоящему пользователю, как будто он её создал.

**Как исправить:** автор всегда из аутентификации, `user_id` в валидацию не пускать:

```php
$data = $request->validate([...]); // user_id здесь отсутствует
$booking = $request->user()->bookings()->create($data);
```

и убрать `user_id` из `#[Fillable]` (или оставить, но никогда не передавать его из запроса).

### C3. `destroy` не проверяет автора

```php
public function destroy($id)
{
    Booking::findOrFail($id)->delete();
    return response()->noContent();
}
```

Любой аутентифицированный пользователь удаляет любую бронь по id — классический IDOR, требования ТЗ
нарушены напрямую.

**Как исправить:** `BookingPolicy::delete()` + `$this->authorize('delete', $booking)`, либо запрос,
ограниченный владельцем, и 404/403 на чужую бронь:

```php
$booking = $request->user()->bookings()->findOrFail($id);
$booking->delete();
```

Обратите внимание: 403 «это чужая бронь» раскрывает существование брони; 404 безопаснее. Любой из вариантов
приемлем, главное — не удалять чужое и покрыть тестом.

### C4. Валидации входных данных нет вообще

`$request->validate(...)` отсутствует. Последствия по каждому полю:

| Ввод | Что происходит |
| --- | --- |
| нет `starts_at`/`ends_at` | SQL-запрос выполняется раньше `Carbon::parse` → Postgres: `invalid input syntax for type timestamp: ""` → **500** |
| `starts_at = "вчера"` | 500 (исключение парсинга Carbon) |
| нет `title` | `NOT NULL` в БД → **500** |
| `room_id = 999` | нарушение FK → **500** |
| `room_id = "abc"` | ошибка приведения типа в Postgres → **500** |
| `ends_at` раньше `starts_at` | бронь создаётся (см. M2) |

По ТЗ нужны понятные 422.

**Как исправить:** `FormRequest` (или `$request->validate`) с правилами `required|integer|exists:rooms,id`,
`required|string|max:255`, `required|date` для времени, `required|date|after:starts_at` для конца, и
`withValidator`/`after` — для проверок бизнес-правил (см. ниже). Валидировать **до** любого запроса в БД.

### C5. Рабочие часы проверяются в таймзоне клиента и только по часу старта

```php
$start = Carbon::parse($request->starts_at);
if ($start->hour < 9 || $start->hour >= 20) { ... }
```

Три ошибки в четырёх строках:

1. `Carbon::parse("2026-11-02T10:00:00+07:00")` **сохраняет смещение клиента**, поэтому `->hour` — час в
   зоне, которую прислал клиент, а не в зоне офиса. `19:00+00:00` (22:00 в Москве) проходит проверку;
   `10:00+07:00` для московской комнаты проходит, хотя это 06:00 MSK.
2. Проверяется только `starts_at`; `19:30–20:30` создаётся беспрепятственно.
3. Проверяется только час, а не полное время: `09:00–20:00` — это границы, которые надо проверять
   как `start >= 09:00` и `end <= 20:00` в зоне офиса.

**Как исправить:** привести оба времени к зоне офиса и проверить границы явно:

```php
$tz = $room->office->timezone; // Europe/Moscow | Asia/Novosibirsk
$start = CarbonImmutable::parse($data['starts_at'])->setTimezone($tz);
$end   = CarbonImmutable::parse($data['ends_at'])->setTimezone($tz);
$open  = $start->setTime(9, 0);
$close = $start->setTime(20, 0);

if ($start->lt($open) || $end->gt($close)) {
    // 422: бронь должна целиком укладываться в 09:00–20:00 по времени офиса
}
```

Полуночь (закрытие в 20:00) означает, что бронь не может пересекать календарный день — это следствие
правила, отдельная проверка не нужна.

### C6. Время не нормализуется к UTC: данные в БД в «зоне клиента»

Колонки объявлены как `$table->timestamp('starts_at')` — в PostgreSQL это `timestamp(0) without time zone`,
то есть «настенное» время без зоны. При записи Eloquent форматирует значение как `Y-m-d H:i:s`, **отбрасывая
смещение** из ISO-строки: `2026-11-02T10:00:00+07:00` сохранится как `2026-11-02 10:00:00`, хотя это 03:00 UTC.
То же самое при сравнении в SQL: Postgres для `timestamp without time zone` игнорирует указанный офсет в литерале.

Итог: два клиента, бронирующие **один и тот же физический слот** в новосибирской комнате, но присылающие
разные смещения (`10:00+07:00` и `03:00+00:00`), получат **разные строки в БД** и проверка конфликтов их не
сопоставит — двойная бронь. Плюс в `index` значения уедут клиенту как UTC-«настенка».

**Как исправить:**

- хранить в UTC и в колонке с зоной: `$table->timestampTz('starts_at')` (`timestamptz` в PostgreSQL);
- нормализовать явно на входе: `CarbonImmutable::parse($value)->utc()` — и только потом писать;
- читать/отдавать в зоне офиса (`->setTimezone($room->office->timezone)`);
- зафиксировать поведение тестом: создать бронь с `+07:00` и с `+00:00` на один и тот же момент — должна быть
  одна бронь, а сохраниться должны одинаковые `timestamptz`.

## Major

### M1. Пересечение считается как «касание»

```php
AND starts_at <= '{$request->ends_at}'
AND ends_at >= '{$request->starts_at}'
```

При `10:00–11:00` и запросе `11:00–12:00` условие `starts_at <= '12:00' AND ends_at >= '11:00'` истинно,
и пользователь получает 409 «Комната занята». По ТЗ встречи «впритык» разрешены, то есть интервалы
полуоткрытые: `[start, end)`.

**Как исправить:** строгие неравенства:

```php
->where('starts_at', '<', $end)
->where('ends_at', '>', $start)
```

### M2. Нет проверки, что `ends_at` позже `starts_at`

`10:00–09:00` и `10:00–10:00` создаются: проверка конфликта для перевёрнутого интервала чаще всего ничего
не находит, а проверка рабочих часов смотрит только на старт. В БД появляется «отрицательная» бронь,
которая ломает и `today`, и будущие отчёты.

**Как исправить:** правило `'ends_at' => ['required', 'date', 'after:starts_at']` (для строгого «позже»).
Дополнительно — `CHECK (ends_at > starts_at)` в миграции как последняя линия обороны.

### M3. Нет проверки длительности и шага 15 минут

Требование «15 минут – 4 часа, шаг 15 минут» не реализовано вообще: пройдут и 1 минута, и 5 часов, и `10:07`.

**Как исправить:** после нормализации к зоне офиса:

```php
$minutes = $start->diffInMinutes($end);            // 15..240
$onGrid  = $start->minute % 15 === 0 && $start->second === 0
        && $end->minute   % 15 === 0 && $end->second   === 0;

if ($minutes < 15 || $minutes > 240) { /* 422: длительность */ }
if (! $onGrid) { /* 422: шаг 15 минут */ }
```

Важно: сетку проверять **в зоне офиса** — при смещении `+05:30` (не наш случай, но в общем виде) 15-минутная
сетка UTC и локальная сетка не совпадают.

### M4. Конец брони не проверяется на рабочие часы

Следствие C5, но это отдельное нарушение правила: `19:00–23:00` проходит, потому что `19 < 20`.

**Как исправить:** проверять `$end->gt($close)` (см. C5) — отдельным сообщением «бронь должна закончиться
не позже 20:00 по времени офиса».

### M5. Гонка двух одновременных запросов

Между `SELECT` конфликтов и `INSERT` нет ни транзакции, ни блокировки: два запроса одновременно увидят
«свободно» и оба вставят бронь.

**Как исправить** (бонусная часть, три варианта по возрастанию надёжности):

1. `DB::transaction()` + `Room::whereKey($id)->lockForUpdate()->first()` — сериализует все бронирования
   одной комнаты (просто, но держит блокировку на всю транзакцию);
2. advisory lock на комнату: `SELECT pg_advisory_xact_lock(?)` с `room_id` — то же, но без блокировки строки;
3. ограничение на уровне БД: `btree_gist` + `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at) WITH &&)`
   — единственный вариант, который защищает и от запросов в обход приложения.

Рекомендую (3) как основу + (1) для понятной ошибки 409, а не 500 от нарушения ограничения.

### M6. `today` считает «сегодня» в UTC и не видит брони через полночь

```php
return $room->bookings()->whereDate('starts_at', today())->get()
```

`today()` — это полночь в `config('app.timezone')`, то есть UTC. Для Новосибирска (`UTC+7`) «сегодня»
смещается на 7 часов: с 00:00 до 07:00 местного времени метод отдаёт **вчерашние** брони, а вечерние
брони последнего дня — наоборот, не отдаёт. Дополнительно: бронь `23:00–00:30` в список не попадёт вовсе
(она начинается «сегодня», но `whereDate` смотрит только на `starts_at`... точнее, попадёт по старту, но
`ends_at` будет уже завтра — а бронь `18:00–01:00` следующего дня, начавшаяся вчера, не попадёт).

**Как исправить:** считать границы дня в зоне офиса и использовать диапазон по пересечению:

```php
$tz    = $room->office->timezone;
$day   = CarbonImmutable::now($tz)->startOfDay();
$from  = $day->utc();
$to    = $day->addDay()->utc();

return $room->bookings()
    ->with('user')
    ->where('starts_at', '<', $to)
    ->where('ends_at', '>', $from)
    ->orderBy('starts_at')
    ->get();
```

### M7. N+1 в `today`

`->map(fn ($b) => ['author' => $b->user->name])` обращается к связи в цикле — по одному запросу на бронь.

**Как исправить:** `->with('user')` перед `get()` (см. M6) и/или `->with('user:id,name')`.

### M8. Без `Accept: application/json` — 500 вместо 401

Это не строка контроллера, но воспроизводится на всех его маршрутах: `auth:sanctum` выбрасывает
`AuthenticationException`, Laravel пытается редиректить на `route('login')`, которой нет, — 500.

**Как исправить:** в `bootstrap/app.php` принудительно отвечать JSON для `api/*`:

```php
->withExceptions(function (Exceptions $exceptions) {
    $exceptions->shouldRenderJsonWhen(
        fn (Request $request) => $request->is('api/*') || $request->expectsJson()
    );
})
```

## Minor

### m1. `destroy($id)` без типизации

`DELETE /api/bookings/abc` → `findOrFail('abc')` → Postgres не приведёт строку к `bigint` → 500 вместо 404.
**Как исправить:** route-model binding `public function destroy(Request $request, Booking $booking)` —
тогда 404 отдаёт фреймворк, а `$booking->id` уже `int`.

### m2. `store` отвечает 200 и отдаёт модель

По REST создание — 201 + `Location`. Возврат модели напрямую раскрывает все колонки (включая `user_id`).
**Как исправить:** `BookingResource` + `return (new BookingResource($booking))->response()->setStatusCode(201)`.

### m3. Формат ответа `today`

`$b->starts_at . ' – ' . $b->ends_at` — это `Carbon::__toString()`, то есть `"Y-m-d H:i:s"` в **UTC**,
без смещения. Это не ISO 8601 и не то, что принимает `store`. Для новосибирской комнаты время в ответе
отличается от локального на 7 часов, то есть пользователь видит не то, что бронировал.
**Как исправить:** отдавать ISO 8601 в зоне офиса (`$b->starts_at->setTimezone($tz)->toIso8601String()`)
и добавить `id`/`title`, чтобы по ответу можно было сделать `DELETE`.

### m4. `index`: лишний `orderByRaw` и нет комнаты

`orderByRaw('starts_at DESC')` — не инъекция (нет пользовательского ввода), но сырой SQL там не нужен:
`orderByDesc('starts_at')`. Важнее: в ответе нет данных о комнате, поэтому «Мои брони» не показывает, где
встреча. **Как исправить:** `->with('room:id,name,office_id')` + API Resource, сортировка
`orderByDesc('starts_at')->orderByDesc('id')` для стабильной пагинации.

### m5. Индексы и ограничения

На `bookings` нет индекса под запрос конфликтов; при росте таблицы `SELECT` по `room_id` + диапазону времени
станет seq scan. **Как исправить:** `$table->index(['room_id', 'starts_at', 'ends_at'])` (или частичный
индекс с `ends_at > now()`), плюс `CHECK (ends_at > starts_at)` и, для M5, exclusion constraint.

### m6. Несогласованные ошибки

Конфликт отдаёт `{"error": "..."}` со статусом 409, а валидация Laravel — `{"message": ..., "errors": {...}}`
с 422. Клиенту приходится поддерживать две ветки разбора. 409 для конфликта семантически корректен, но по ТЗ
«понятные ошибки валидации (422)» — безопаснее отдавать 422 с `errors.ends_at` и текстом, включающим
конфликтующий интервал. Главное — единый формат.

### m7. 409 отдаётся до валидации

Запрос с несуществующей комнатой и «плохим» временем всё равно проходит проверку конфликтов первой и может
вернуть 409 — то есть код проверки конфликта работает как оракул занятости до авторизации/валидации.
**Как исправить:** валидация → существование комнаты → проверка правил → конфликт.

### m8. Отмена брони не логируется

Создание пишется в `bookings.log`, удаление — нет, хотя отмена брони это ровно то событие, которое
разбирают в спорных ситуациях. **Как исправить:** `Log::channel('bookings')->info('Booking cancelled', [...])`
до `delete()`.

### m9. Нет политики

Проверка авторства сейчас «размазана» по контроллеру (и в `destroy` её нет вовсе). **Как исправить:**
`BookingPolicy` (`view`, `delete`) + `$this->authorize()`; это же переиспользуется, если появится `show`/`update`.

## Подозрительно, но не проблема

- **`DB::select` сам по себе** — не проблема. Проблема только в интерполяции (C1); с bindings сырой SQL допустим.
- **`orderByRaw('starts_at DESC')`** — сырой SQL, но без пользовательских данных, инъекции нет (m4 — только стиль).
- **Нет ограничений на прошедшие даты, на количество броней, на пересечение своих броней** — по ТЗ «других
  ограничений на даты нет», так что это корректное поведение, а не баг.
- **`paginate(20)` в `index`** — нормально; фильтрация по `user_id` из токена не даёт утечки (в отличие от `destroy`).
- **`Route::delete('/bookings/{id}')` с `{id}`, а не с моделью** — не ошибка, но причина m1.
- **`today(Room $room)` через route-model binding** — 404 на несуществующую комнату отдаёт фреймворк, это правильно.
- **`$request->user()`** — корректно: маршруты под `auth:sanctum`, `user()` не вернёт `null`.
- **Атрибуты `#[Fillable]`/`#[Hidden]`** — актуальный синтаксис Laravel 13, не устаревший `$fillable`.
- **`foreignId(...)->constrained()` без `onDelete`** — не проблема: `NO ACTION` в PostgreSQL защищает от удаления
  комнаты с бронями, а каскадное удаление броней при удалении пользователя — вопрос продукта, не баг.
- **Отсутствие soft deletes** — по ТЗ не требуется; жёсткое удаление допустимо (при условии C3).
- **`Log::withContext(['booking_id' => ...])`** — контекст применяется к последующим записям в рамках запроса;
  для одного запроса с одним логом это работает как задумано.
- **`DatabaseSeeder` с постоянными токенами** — хеш хранится как у обычного токена Sanctum; для демо это ок.
- **`unsignedSmallInteger('capacity')`** — корректный тип; отсутствие каста `integer` в модели не ломает поведение
  на PostgreSQL (`pdo_pgsql` возвращает `int`), см. «Модели».

## Модели и миграции

Типы объявлены аккуратно: у всех связей есть возвращаемые типы, `casts()` на месте, `#[Fillable]` используется
вместо `$guarded`. Содержательные замечания:

- **`Booking`**: `user_id` в `#[Fillable]` — именно это включает C2. Убрать или никогда не передавать из запроса.
  `'starts_at' => 'datetime'` корректно, но для брони лучше `'immutable_datetime'`, чтобы время нельзя было
  случайно мутировать в `$b->starts_at->addHour()`.
- **`Office`**: `timezone` — просто строка, без валидации значения (валидатор `timezone` в `FormRequest`/сидере
  не помешает), без каста. Удобно добавить `bookings(): HasManyThrough` — пригодится для отчётов по офису.
- **`Room`**: `capacity` без каста `'integer'`; на PostgreSQL это не проявляется, но при переходе на SQLite в тестах
  тип «поедет».
- **Миграция `bookings`**: `timestamp` вместо `timestampTz` — корень C6; нет индекса (m5) и `CHECK`.

## Идеи (не дефекты)

- **Эндпоинт свободных комнат**: `GET /api/rooms/free?office_id=&from=&to=&capacity=` — один запрос вместо
  перебора комнат на клиенте; реализуется тем же условием «нет пересечения» + `whereDoesntHave('bookings')`.
- **`GET /api/bookings/{id}` и `PATCH`** для переноса встречи (с той же валидацией и политикой).
- **Идемпотентность создания**: заголовок `Idempotency-Key`, чтобы двойной клик не создавал две брони.
